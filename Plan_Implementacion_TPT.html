1 Resumen Ejecutivo

La Plataforma TPT (Transferencia al Puesto de Trabajo) de MSO Chile es una herramienta integral que soporta el ciclo completo de gestion de programas de desarrollo organizacional: desde la definicion de competencias y conductas criticas, pasando por mediciones pre/post mediante encuestas y observaciones de jefatura, hasta la generacion de reportes con inteligencia artificial.

Actualmente, la plataforma opera como una maqueta funcional desplegada en GitHub Pages, cuyo backend se sustenta en Google Apps Script con Google Sheets como base de datos. Si bien este enfoque permitio validar rapidamente la propuesta de valor y la experiencia de usuario, presenta limitaciones severas para un despliegue productivo con multiples clientes simultaneos.

Objetivo de este plan: Detallar la ruta tecnica para migrar la plataforma desde su estado actual de maqueta a una aplicacion productiva en un stack cloud moderno (Next.js + Node.js + PostgreSQL), capaz de soportar de 50 a 500 usuarios concurrentes, multiples organizaciones cliente y operacion 24/7.

Objetivos Estrategicos

  1. Escalabilidad: Pasar de un unico spreadsheet a una base de datos relacional que soporte cientos de organizaciones y miles de registros sin degradacion.
  2. Seguridad: Implementar autenticacion robusta con JWT, control de acceso basado en roles (RBAC) y cifrado en transito y en reposo.
  3. Multi-tenancy: Permitir que multiples clientes operen de forma aislada en la misma instancia de la aplicacion.
  4. Disponibilidad: Garantizar un SLA del 99.5% con infraestructura cloud gestionada, backups automaticos y monitoreo proactivo.
  5. Preservar la UX validada: Mantener el diseno visual y los flujos de usuario ya probados en la maqueta, que reflejan meses de iteracion con usuarios reales.

2.2 Arquitectura Tecnica Actual

Frontend

  • HTML/CSS (Tailwind-like clases utilitarias personalizadas)
  • JavaScript vanilla con carga dinamica de vistas via google.script.run
  • Chart.js para graficos del dashboard
  • SPA simulada: un index.html que carga vistas parciales segun el menu lateral
  • Sin bundler, sin framework reactivo

Backend

  • Google Apps Script (GAS) como servidor
  • Google Sheets como base de datos (26 hojas/tablas)
  • Google Drive para almacenamiento de archivos
  • Sesiones manuales con token en PropertiesService
  • Hash de passwords con Utilities.computeDigest (SHA-256)
  • Audit log integrado en hoja separada

2.3 Limitaciones Identificadas

Limitaciones criticas que impiden el uso productivo:
  • Rendimiento: Google Sheets tiene un limite de 10 millones de celdas y las lecturas completas de hoja se degradan con volumen. La funcion getSheetData() lee TODA la hoja cada vez.
  • Concurrencia: GAS tiene limite de 30 usuarios simultaneos y 6 min/ejecucion. LockService es fragil bajo carga.
  • Seguridad: Tokens de sesion almacenados en PropertiesService sin rotacion. SHA-256 sin salt para passwords. CORS no configurable en GAS.
  • Escalabilidad: No hay indices, no hay queries SQL, no hay relaciones con integridad referencial. Toda busqueda es lineal (filter sobre arrays).
  • Multi-tenancy: Un solo spreadsheet para todos los clientes. Sin aislamiento de datos real.
  • Mantenibilidad: Sin tipado, sin tests, sin CI/CD. Deployments manuales via clasp.
  • Disponibilidad: Sujeto a cuotas de Google (quotas diarias de ejecucion, emailApp, etc.).

2.4 Elementos a Preservar

Activos valiosos de la maqueta que deben mantenerse:
  • Modelo de datos bien estructurado (26 tablas con relaciones claras) — se migra directamente a PostgreSQL
  • Flujos de usuario validados: login/registro, navegacion por programa, builder de encuestas, observaciones
  • Logica de calculo de brechas auto/co PRE/POST por competencia (ReportesService.gs)
  • Interfaz visual limpia con sistema de diseno coherente (colores MSO, layout sidebar)
  • Roles y permisos ya definidos: admin, jefatura, participante, colaborador
  • Integracion con Groq API para reportes con IA ya probada
  • Estructura de estados de ciclo de vida (programa, encuesta, observacion, usuario)

3.3 Autenticacion y Autorizacion

Se implementara un sistema de autenticacion propio basado en JWT con refresh tokens, reemplazando el sistema actual de sesiones en PropertiesService:

  • Access Token (JWT): Firmado con RS256, expira en 15 minutos. Contiene userId, rol, clienteId. Enviado en header Authorization: Bearer <token>.
  • Refresh Token: Opaco (UUID v4), almacenado en Redis con TTL de 7 dias. Rotacion en cada uso (sliding window). Enviado como httpOnly secure cookie.
  • Password Hashing: bcrypt con salt rounds = 12. Reemplaza SHA-256 sin salt actual.
  • RBAC Middleware: Decoradores en cada ruta que verifican rol del usuario contra permisos requeridos. Roles: admin, jefatura, participante, colaborador.
4 Modelo de Base de Datos

El modelo relacional se deriva directamente de las 26 hojas definidas en Config.gs (HOJAS, ENCABEZADOS), normalizando relaciones y agregando integridad referencial con foreign keys, indices y constraints. Se utiliza nomenclatura snake_case y UUIDs como primary keys.

5 Plan de Implementacion por Fases

Fase 1: Fundamentos (Semanas 1-4)

Establecer la base tecnica sobre la cual se construira todo el sistema. Al final de esta fase, se debe tener un esqueleto funcional desplegado en staging con autenticacion completa.

Semana Entregable Detalle
S1 Setup del Proyecto
  • Inicializar monorepo con Turborepo: /apps/web (Next.js), /apps/api (Express), /packages/shared (tipos Zod)
  • Configurar TypeScript strict, ESLint, Prettier en ambos proyectos
  • Configurar base de datos PostgreSQL en Supabase (proyecto staging)
  • Crear schema Prisma inicial con todas las tablas de seccion 4
  • Ejecutar primera migracion (prisma migrate dev)
  • Configurar GitHub Actions: lint + typecheck en cada PR
S2 Sistema de Autenticacion
  • API: POST /auth/register (registro con estado pendiente, bcrypt)
  • API: POST /auth/login (verificacion credentials, emision JWT + refresh token)
  • API: POST /auth/refresh (rotacion de refresh token)
  • API: POST /auth/logout (revocacion de refresh token en Redis)
  • Middleware requireAuth con verificacion JWT RS256
  • Middleware requireRole(['admin']) para RBAC
  • Frontend: Paginas login y registro replicando diseno actual
  • Frontend: Interceptor Axios con auto-refresh de token expirado
S3 CRUD Organizaciones + Usuarios
  • API: CRUD completo /api/organizaciones (solo admin)
  • API: CRUD /api/usuarios con filtros por organizacion, rol, estado
  • API: PATCH /api/usuarios/:id/aprobar (admin aprueba registro pendiente)
  • API: PATCH /api/usuarios/:id/rol (cambio de rol)
  • Frontend: Vista clientes.html migrada a React component
  • Frontend: Vista usuarios.html migrada con tabla paginada, filtros
  • Frontend: Layout principal (sidebar + header + content area) replicando index.html
S4 Deploy Staging + CI/CD
  • Deploy frontend en Vercel (branch staging)
  • Deploy API en Railway (o Render) conectado a Supabase
  • Configurar variables de entorno en ambas plataformas
  • GitHub Actions: deploy automatico staging en merge a develop
  • GitHub Actions: build + test en cada PR
  • Seed de datos de prueba (organizacion demo, usuarios admin/jefatura/participante)
  • Documentacion de API con Swagger/OpenAPI auto-generado
Criterios de Aceptacion Fase 1:
  • Un usuario puede registrarse, ser aprobado por admin, hacer login y navegar el dashboard vacio
  • Admin puede crear organizaciones y gestionar usuarios
  • El deploy en staging funciona con HTTPS y variables seguras
  • CI/CD pasa lint, typecheck y tests basicos

7 Seguridad

7.1 Flujo de Autenticacion

  1. Registro: Usuario envia nombre, email, password, organizacion → API crea usuario con estado pendiente y password hasheado con bcrypt (12 rounds). Admin recibe notificacion.
  2. Aprobacion: Admin revisa y aprueba usuario → estado cambia a activo. Se envia email de bienvenida con Resend.
  3. Login: Usuario envia email + password → API verifica bcrypt, genera Access Token (JWT RS256, 15 min) y Refresh Token (UUID, 7 dias en Redis) → JWT en response body, Refresh en httpOnly cookie.
  4. Requests autenticados: Frontend envia JWT en header Authorization: Bearer. Middleware valida firma, expiracion y extrae userId + rol.
  5. Token Refresh: Cuando JWT expira (401), frontend automaticamente llama a /auth/refresh con cookie. API rota refresh token y emite nuevo JWT.
  6. Logout: Se revoca refresh token en Redis. Frontend limpia estado local.

7.3 Medidas de Seguridad Adicionales

Proteccion de Datos

  • En transito: HTTPS obligatorio (TLS 1.3). HSTS header.
  • En reposo: PostgreSQL con cifrado de disco (Supabase lo incluye). Backups cifrados.
  • Passwords: bcrypt con cost factor 12. Nunca se almacena en texto plano.
  • Datos sensibles: Refresh tokens hasheados en DB. API keys en variables de entorno.

Proteccion de Aplicacion

  • CORS: Whitelist explicita de origenes permitidos.
  • Rate Limiting: 100 req/min general, 5 req/min en /auth/login (prevenir brute force).
  • Input Validation: Zod schemas en cada endpoint. Sanitizacion de HTML.
  • SQL Injection: Prisma ORM con queries parametrizados.
  • XSS: React escapa por defecto. CSP headers.
  • CSRF: SameSite cookies + validacion de origin.

Riesgo OWASPMitigacion Implementada
A01: Broken Access ControlRBAC middleware en cada ruta. Verificacion de pertenencia a organizacion (multi-tenant isolation).
A02: Cryptographic Failuresbcrypt para passwords, RS256 para JWT, TLS 1.3, cifrado en reposo.
A03: InjectionPrisma ORM (parametrizado), Zod validation, sanitize-html para texto rico.
A04: Insecure DesignPrincipio de menor privilegio. Roles con acceso minimo necesario.

8.5 Estrategia de Backups

  • Base de datos: Backup automatico diario via Supabase (retencion 30 dias en Pro). Point-in-time recovery disponible.

Conclusion

La Plataforma TPT cuenta con una base solida: un modelo de datos bien estructurado, flujos de usuario validados y logica de negocio probada en la maqueta actual. La migracion a un stack moderno (Next.js + Node.js + PostgreSQL) es un paso natural que permitira a MSO Chile escalar su operacion a multiples clientes simultaneos con la confiabilidad, seguridad y rendimiento que un producto SaaS requiere.

Con un equipo compacto de 2-3 personas y una inversion de USD $26-34K en el primer ano (incluyendo desarrollo e infraestructura), la plataforma puede estar en produccion en 20 semanas, atendiendo de 50 a 500 usuarios concurrentes.

El momento de comenzar es ahora.
